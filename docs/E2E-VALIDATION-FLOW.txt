==================================================================================================
 CLAIMS PLATFORM - END-TO-END VALIDATION FLOW  (manual test script)
==================================================================================================
 Project   : Claims Platform - frontend/ (Angular 22)  +  backend/ (Spring Boot)
 Purpose   : Follow this top to bottom to prove the whole system works - UI and backend together -
             for all three roles (Claimant, Claims Officer, Manager).
 How to use: Do each step under "DO", compare with "EXPECT", tick the [ ] box. If something does not
             match, write down the step number and what you saw (see the results sheet at the end).

 Every number in the EXPECT lines was produced by running this exact flow against the real backend
 (fresh database) before this file was written. Claim numbers are random, so write down yours.
 The steps about the form's messages and about documents (3.1, 3.2, 3.2A, 3.3, 5.4, 6.5A, 7.9, Part 10) were added on 2026-10-26 and
 checked against the running application, but the whole flow was not replayed from the top after those additions.

 Roughly 25-30 minutes for the whole flow.


==================================================================================================
 PART 0 - BEFORE YOU START
==================================================================================================

 0.1  What you need installed
      [ ] JDK 21+ and Maven          (for the backend)
      [ ] Node 22.22.3+, 24.15+ or 26+ and npm  (for the UI; Angular 22's range)   check: node --version

 0.2  Start the BACKEND  (folder: backend/ in this repository)
          mvn spring-boot:run
      Wait for the log line:   Started ClaimsManagementApplication
      [ ] Open http://localhost:8080/swagger-ui/index.html  -> the Swagger page loads
      IMPORTANT: the database is in memory. EVERY restart of the backend erases all accounts and
      claims. Restart it before this flow so you start clean (expected: no claims at all).

 0.3  Start the UI  (folder: frontend/ in this repository)
          npm install        (first time only)
          npm start
      [ ] Open http://localhost:4200  -> you land on the sign-in page (title: "Claims Platform").
      The UI talks to the backend through a proxy (proxy.conf.json: /api -> localhost:8080), so
      always use http://localhost:4200 in the browser, never open the backend URL for the UI.

 0.4  Browser tip - switching between users
      The signed-in session is saved in the browser (localStorage), which is SHARED between tabs.
      Safest: use ONE tab and "Sign out" before signing in as someone else.
      Nicer: use a normal window for the officer/manager and a private (incognito) window for
      claimants, so you can watch both sides at once.

 0.5  Accounts used in this flow
      +-----------+-------------------------------+--------------+----------------------------+
      | Role      | Email                         | Password     | How you get it             |
      +-----------+-------------------------------+--------------+----------------------------+
      | Officer   | officer@claims.local          | ChangeMe123! | seeded by the backend      |
      | Manager   | manager@claims.local          | ChangeMe123! | seeded by the backend      |
      | Claimant  | alice.tan@example.com         | Passw0rd!A1  | you register it (Part 2)   |
      | Claimant  | bob.lim@example.com           | Passw0rd!B1  | you register it (Part 2)   |
      +-----------+-------------------------------+--------------+----------------------------+
      The sign-in page has "Local demo accounts" buttons that fill in the officer or manager email and password; click "Sign in" afterwards.

 0.6  The three claims you will create  (incident date: any day from 7 days ago up to today; the form allows nothing older)
      +----+----------+----------+--------+--------+-----------------+----------------------------+
      |    | Claimant | Type     | Market | Amount | Policy number   | Description (>= 20 chars)  |
      +----+----------+----------+--------+--------+-----------------+----------------------------+
      | C1 | Alice    | Motor    | SG     | 2400.75| (generated)     | Rear bumper damaged when   |
      |    |          |          |        |        |                 | another car reversed into  |
      |    |          |          |        |        |                 | mine in a car park.        |
      | C2 | Alice    | Property | HK     | 1000.00| (generated)     | Burst water pipe flooded   |

      The policy number is generated by the form (POL-year-six digits): leave it as it is. Markets are chosen from a
      dropdown: SG = Singapore, HK = Hong Kong, MY = Malaysia (the other three are IN, TH, ID).
      Create them in the order C1, C2, C3 (the queue is "oldest first", so order matters).
      Write down the claim numbers you get:   C1 = ____________  C2 = ____________  C3 = ____________

 0.7  The story you are about to play
      C1  Alice's motor claim : picked up -> review -> officer asks a question -> Alice answers ->
                                approved -> settled                                (happy path)
      C2  Alice's property claim: manager assigns it to the officer -> review -> rejected  (reject path)
      C3  Bob's claim         : nobody touches it - it stays waiting in the queue
                                (so the dashboard always has an "unassigned" claim to show)

 [ ] Signed out,  /queue or /dashboard or /claims/new      -> sign-in page (/login)

       Claimant : My claims | Report an incident
       Officer  : Work queue | Assigned to me
       Manager  : Dashboard | Work queue | All claims
 [ ] A manager sees NO "Pick up" button in the queue (only officers can pick up); a manager assigns
     from the claim page instead (Part 8).

 Note: these redirects are only convenience in the UI. The real protection is in the backend - the
 same restrictions were also verified by calling the API directly (e.g. a claimant calling the queue
 gets HTTP 403; another person's claim gets HTTP 404).


==================================================================================================
 PART 11 - RESILIENCE
==================================================================================================

 11.1 Refresh keeps you signed in.
      DO: Signed in as anyone, press F5.     EXPECT: [ ] still signed in on the same page.

 11.2 Sign out is final.
      DO: Click "Sign out", then press the browser Back button.
      EXPECT: [ ] you end on the sign-in page, not on claim data.

 11.3 Backend unreachable.
      DO: Stop the backend (Ctrl+C in its terminal). In the UI, as the manager, open Dashboard and click "Refresh".
      EXPECT: [ ] Red message "Cannot reach the server. Check that the backend is running and try again."
              [ ] The page does not crash or go blank, and the Refresh button still works.
      (Technical note: in development the UI's proxy answers "502 Bad Gateway" with an empty body when the
       backend is down; the UI recognises that and shows this message. Checked by calling the proxy while
       the backend was stopped.)

 11.4 Backend restarted = data gone (the database is in memory).
      DO: Start the backend again. Reload the UI while still signed in as Alice (or Bob).
      EXPECT: [ ] You are sent back to the sign-in page (the account no longer exists, the backend answers
                  401, and the UI signs you out). The seeded officer/manager can sign in again; their
                  claim list is empty.
      This is expected behaviour, not a bug. Re-register Alice/Bob to run the flow again.

==================================================================================================
 THINGS THAT LOOK ODD BUT ARE NOT BUGS
==================================================================================================
 - Picking up a claim does not change its status. It stays "Submitted" until the officer clicks
   "Start review". (Backend rule.)
 - "Unassigned" on the dashboard counts every claim with no officer, whatever its status.
   "Open claims" = Submitted + Under review + Awaiting information + Approved.
 - Liability has no currency symbol. The backend stores only a 2-letter market code, so amounts are
   shown with their market ("2,400.75 SG"), and the grand total is labelled "unconverted, mixed markets".
 - A claimant can see the name of the officer on their claim - the backend sends it.
 - Only ONE officer is seeded, so two officers racing to pick up the same claim cannot be tried by hand.
   (That case - "already assigned to another officer" - is covered by the automated tests instead.)
 - The Status filter is the only filter on the claims lists - the backend offers no search.
 - Claim numbers look like CLM-8D45968B-EDE and are random every run.

 Symptom                                           Likely cause / what to do
 ------------------------------------------------  -----------------------------------------------
 Sign-in says "Cannot reach the server"            Backend not running or still starting. Check
                                                   http://localhost:8080/v3/api-docs returns JSON.
 Browser console shows a CORS error                You opened the UI on a different address/port.
                                                   Use http://localhost:4200 started with "npm start"
                                                   (the proxy is what makes CORS unnecessary).
 "An account with this email already exists"       The backend has not been restarted since your last
                                                   run. Restart it for a clean database.
 Numbers on the dashboard are higher than expected Leftover data from a previous run. Restart backend.
 Page title/tab shows "Claims" but page is blank   Check the browser console and the "npm start" terminal
                                                   for build errors.
 Signed out unexpectedly                           Backend restarted (see 11.4) or the token expired
                                                   (valid for 24 hours).
